# 第 3 批内容优化对比

本批不是把技术原文直接翻译成长说明，而是先回答普通用户最关心的三个问题：能做什么、怎么开始、有哪些限制。全部案例标为“演示性示例，尚未实际运行验证”。

| Skill | 优化前常见理解障碍 | 优化后的表达重点 |
| --- | --- | --- |
| 飞书 Markdown 文件助手 | 容易把 `fetch / diff / patch / overwrite` 当作只有开发者才懂的命令，也容易和飞书云文档混淆 | 先说明是飞书云盘里的原生 Markdown；用“读取、比较、只替换一处、整篇覆盖”解释能力，并说明局部替换也会整篇写回 |
| 按需求实施代码 | 容易被理解成从想法到上线的全自动开发 | 明确只接手已经确认的一个任务；当前分支需准备好，产物是代码、测试和提交，不包含 PR、关单或上线 |
| 大型项目决策地图 | “frontier、map、HITL”等术语会遮住实际用途 | 用毕业设计案例解释“先定终点—拆未知问题—标依赖—找当前可推进任务”，并强调默认只规划 |
| 界面设计与体验检查 | 设计、实现、改进、审查几个流程容易混在一起 | 简明版概括整体能力，示例只展示一次真实的只读审查；详细版再区分设计、改进、规范提取和审查 |
| Remotion 视频制作规范 | 容易误以为安装后会得到一个视频剪辑软件，或完成代码就自动生成 MP4 | 先说明视频由 React 代码生成；把 Studio 预览放在流程中心，明确“用户确认前不导出” |

## 更容易理解的地方

- 简明版优先说明使用价值和典型场景，不在首屏堆叠命令、协议或内部模块名。
- 功能介绍解释“能做什么”，使用示例展示“一次真实操作”，两者不再重复列功能。
- 专业术语只有在影响准备工作或风险边界时才保留，并先配普通语言解释。
- 每条都明确 Skill 不是独立软件，需要通过支持 Skill 的 AI 工具使用。

## 更准确的地方

- 飞书 Markdown 的 `patch` 被准确描述为下载后替换再覆盖，而不是并发安全的在线局部编辑。
- `implement` 被限定为一个已确定任务，补充了当前分支、提交、PR 和关单边界。
- `wayfinder` 明确会写入问题跟踪器，并区分规划与执行。
- `ui-taste` 区分免费基础 Skill 与可选付费 MCP，审查示例不伪装成已修复。
- Remotion 明确默认只预览、不渲染，并补充版本、素材许可和计算资源要求。

## 事实、推断与示例

- `reviewEvidence.sourceFacts`：可直接从原始 `SKILL.md` 或其引用资料确认的事实。
- `reviewEvidence.reasonableInferences`：基于原文工作方式得出的合理使用建议，不冒充原文承诺。
- `reviewEvidence.untestedClaims`：本轮没有真实账号、项目或渲染环境支持的示例与结果，前台统一标为演示性内容。
