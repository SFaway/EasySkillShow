# 第 4 批内容优化对比

本批 3 条内容继续采用“简明版先回答为什么用，详细版再回答怎么用”的结构。示例只展示一次完整任务，并统一标记为未经实测。

| Skill | 原始文档的理解门槛 | 优化后的用户表达 |
| --- | --- | --- |
| 人工配置向导生成器 | 原文直接介绍 Bash 模板、`.env`、`gh secret` 和阶段函数，新手容易误以为 AI 会替自己登录并完成全部配置 | 先解释它把“只能由人操作的配置”变成逐步终端向导；明确用户亲自登录、密钥隐藏输入、AI 只静态检查脚本 |
| Azure 云服务故障诊断 | 服务、命令和监控工具很多，容易把“能查询”误解为“已经找到并修复根因” | 用“症状—资源健康—日志—指标—近期变更”说明排障顺序；示例采用只读证据分析，诊断、验证和生产修改分开 |
| Google ADK 智能体开发参考 | ADK、Agent、callback、state、graph workflow 与多个配套 Skill 密集出现，容易被理解成一键生成并部署智能体 | 先说明它只负责代码阶段；把需求确认、示例研究、脚手架、编码、快速检查、评测和部署按顺序拆开 |

## 更容易理解的地方

- 三个简明版都直接给出用户的现实任务：配置项目、排查云故障、给已有智能体项目加功能。
- 示例说明用户要提供什么、AI 具体做哪几步以及最终可能得到哪些文件或报告。
- “Skill 不是独立软件”的解释放进详细介绍，并与 Bash、Azure 控制台和 agents-cli 的实际环境对应。
- 功能介绍讲通用能力，使用示例只讲一个具体任务，避免重复列功能。

## 更准确的地方

- `wizard` 不再被描述成全自动配置工具：它生成脚本、要求人运行，并且不会端到端代跑。
- Azure 诊断支持“仅依据现有证据”的只读模式；实时访问、根因验证和生产修复被明确区分。
- Google ADK 条目保留了完整套件依赖，明确该 Skill 不负责脚手架、评测、部署或发布。
- 精确安装量无法复核时保持 `null`；GitHub Stars 只作为仓库级指标。

## 事实、推断与示例

- `reviewEvidence.sourceFacts` 只记录原始 `SKILL.md`、模板或直接引用资料明确支持的内容。
- `reviewEvidence.reasonableInferences` 保存面向 EasySkillShow 用户的谨慎使用建议。
- `reviewEvidence.untestedClaims` 明确记录本轮没有实际运行的账号、脚本、云资源、项目和模型调用。
