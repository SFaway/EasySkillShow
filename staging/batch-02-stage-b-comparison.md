# Batch 02 · Stage B 内容优化对比

## 统一改写原则

本批沿用通过审核的 PPTX 样例标准：简明版先回答“能做什么、适合什么场景、会得到什么”；详细版再解释使用步骤、环境要求和能力边界；底层术语只有在帮助用户判断能否使用时才出现。所有案例都明确标注为“演示性示例，尚未实际运行验证”。

| Skill | 优化前常见理解障碍 | 优化后的变化 |
| --- | --- | --- |
| grilling | 原名难以理解，容易误以为只是激烈质问 | 改为“分轮决策追问”，解释决策树、推荐答案、逐轮确认和停止条件；明确不会自动执行方案 |
| teach | 容易被理解成一次性生成教程 | 说明它会建立长期学习工作区，生成短课、练习和学习记录；把固定文件产物与学习效果边界分开 |
| code-review | “双轴”“fixed point”等术语对新手不友好 | 用“项目规范”和“需求实现”两类检查解释双轴；把固定点翻译为明确且稳定的 Git 基准点 |
| vercel-react-best-practices | 规则类别多，容易变成技术名词堆积 | 简明版突出请求串行、包体积和重复渲染三类直观问题；详细版保留 70 条、8 类等准确事实 |
| lark-doc | 用户可能以为是本地 Word 工具或免授权插件 | 明确它处理飞书云文档，需要登录和权限；突出写前确认、最小修改、写后复核，以及整篇覆盖风险 |

## 准确性改进

- 事实：只写入原始 `SKILL.md` 和直接相关资料中能够确认的能力、依赖、文件结构与流程。
- 合理推断：如“适合实习前学习 SQL”“适合 PR 前复核”，单独放入 `reasonableInferences`，不伪装成原文承诺。
- 未经实测：所有输入输出案例、当前环境兼容性和实际效果放入 `untestedClaims`，并在页面示例中直接提醒。
- 统计：不把四舍五入的页面数转换为虚假的精确安装次数。

## 重复控制

功能介绍说明“为什么用、能解决什么”；使用示例只演示一次真实任务中的“给什么、怎么说、可能得到什么”。详细版不重复罗列示例中的全部步骤，而是解释可复用的通用工作流。
